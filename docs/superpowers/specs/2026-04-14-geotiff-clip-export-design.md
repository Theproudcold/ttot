# GeoTIFF 裁剪导出设计

## 背景

当前工具已经支持：

- 本地上传 `GeoTIFF`
- 预览单波段或多波段影像
- 绘制围栏、生成网格
- 导出围栏和网格的 `GeoJSON`
- 基于分类方案的地图着色与 hover 信息展示

但现有导出能力仍有明显缺口：

1. 只能导出围栏和网格的矢量结果，不能导出栅格结果
2. 用户已经明确提出，希望支持 `tif` 导出，且最好可选
3. 当前“围栏 + 影像”的核心工作流已经形成闭环，缺的就是把围栏裁剪后的原始栅格带走

经过确认，本次用户要的不是“分类结果图导出”，而是：

- 导出原始影像的裁剪结果
- 输出格式为 `GeoTIFF`
- 裁剪方式按围栏最小外接矩形
- 围栏外像元写 `NoData`
- 保留原始全部波段

## 目标

### 业务目标

- 让用户可以把围栏对应的原始栅格子集导出为 `GeoTIFF`
- 保留原始坐标参考、分辨率和全部波段，方便后续 GIS 或遥感分析

### 体验目标

- 导出入口简单直接，不把现有左侧导出区搞成花里胡哨的菜单
- 导出前置条件清晰：没有影像或围栏时不允许触发
- 导出过程有明确状态反馈，避免用户误以为卡死

### 非目标

- 本次不导出当前分类方案的彩色结果图
- 本次不支持不规则边界栅格输出，只支持矩形包络裁剪
- 本次不做服务端导出，先以纯前端方案为主
- 本次不导出网格统计值为栅格
- 本次不做多种导出格式切换 UI

## 方案比较

### 方案 1：导出当前分类结果为 `GeoTIFF`

优点：

- 和当前页面可视结果一致，用户一眼就懂
- 更适合汇报、成果展示

缺点：

- 输出的是派生结果，不是原始分析数据
- 会把前端渲染逻辑和导出逻辑绑定得过死
- 不符合当前用户明确选择的方向

### 方案 2：导出围栏裁剪后的原始 `GeoTIFF`

优点：

- 保留原始像元值，适合后续分析
- 输出更接近 GIS/遥感工作流里的标准中间结果
- 与当前“上传原始影像 -> 圈定区域 -> 导出子集”逻辑一致

缺点：

- 需要补齐 `GeoTIFF` 写出链路
- 用户不能直接拿到“当前彩色分类图”那种成果图

### 结论

采用 **方案 2**。

## 导出规格

### 输入

- 原始上传的 `GeoTIFF` 文件
- 当前围栏几何

### 输出

- 一个新的 `GeoTIFF` 文件
- 空间范围为围栏最小外接矩形
- 保留原始全部波段
- 保留原始 CRS、origin、resolution、像元排列方向
- 围栏外像元写为 `NoData`

### 裁剪规则

1. 先读取围栏的包络框
2. 将包络框映射到原始影像像元窗口
3. 读取该窗口对应的全部波段数据
4. 对窗口内每个像元判断其中心点是否落在围栏内
5. 若不在围栏内，则该像元各波段写成 `NoData`
6. 将结果写出为新的 `GeoTIFF`

### NoData 规则

- 如果原始影像已有 `NoData`，优先复用原值
- 如果原始影像没有明确 `NoData`，为导出结果设置一个新的 `NoData`
- 新 `NoData` 的选取必须避免和正常像元值明显冲突
- 导出元数据中应写入该 `NoData`，避免下游软件误读

## UI 设计

### 导出入口

在左侧现有导出区增加一个新按钮：

- `导出 GeoTIFF`

按钮位置与现有：

- `导出围栏`
- `导出网格`

保持同一组工具按钮，不额外新增下拉菜单。

### 按钮状态

以下任一条件不满足时按钮禁用：

- 未加载影像
- 未生成围栏
- 当前正在执行导出

### 反馈方式

- 导出进行中：按钮文案或附近提示显示“正在导出 GeoTIFF”
- 导出成功：回到可点击状态
- 导出失败：给出明确错误提示，例如“围栏超出影像范围”或“GeoTIFF 写出失败”

## 数据流设计

### 现有能力复用

- `useRasterStore` 已持有原始上传文件 `sourceFile`
- `useFenceStore` 已持有当前围栏几何
- `src/shared/geo/raster.ts` 已有读取 `GeoTIFF` 的基础能力

### 新增职责

建议新增一个单独导出模块，职责如下：

- 读取原始文件并获取首图像对象
- 计算围栏包络对应的像元窗口
- 读取窗口栅格数据
- 生成围栏内掩膜
- 将围栏外像元写成 `NoData`
- 组装写出所需的元信息
- 触发浏览器下载

不要把这些导出细节直接塞进 `LeftPanel.tsx`，不然左栏会胖成球。

## 技术方案

### 读取

继续使用现有的 `geotiff` 读取链路，从本地 `File` 读取原始影像。

### 写出

当前项目只有 `GeoTIFF` 读取能力，没有写出能力。

因此实现时需要：

- 引入一个适合前端写出 `GeoTIFF` 的库，或
- 基于现有 `geotiff` 生态补齐编码方案

实现选型要求：

- 能写多波段
- 能设置地理参考信息
- 能写 `NoData`
- 能在浏览器里生成 `Blob` 或 `ArrayBuffer`

### 性能约束

- 优先按围栏包络窗口读取，而不是整图读完再裁
- 纯前端导出在大图下仍可能耗时较长，因此必须提供导出状态提示
- 如果后续发现主线程阻塞明显，再考虑移入 `Web Worker`

## 错误处理

需要明确处理以下情况：

- 没有上传影像
- 没有围栏
- 围栏包络越界
- 影像缺少必要地理参考参数
- 写出库编码失败
- 浏览器下载失败

错误提示应尽量面向用户，而不是直接把底层异常原样甩出去。

## 测试策略

至少覆盖以下层次：

### 纯函数 / 导出模块测试

- 围栏包络到像元窗口的换算
- 围栏外像元写 `NoData`
- 多波段裁剪结果维度正确
- 导出元信息保留 CRS / resolution / origin

### 组件测试

- 无影像或无围栏时 `导出 GeoTIFF` 按钮禁用
- 具备条件时按钮可点击
- 点击后触发 GeoTIFF 导出流程
- 导出中状态能正确显示

## 风险与约束

### 风险 1：前端写出库能力不足

如果选型的写出库无法完整保留地理参考或多波段元数据，导出结果会变成“看着像 tif，实际 GIS 不认”的废物。

控制策略：

- 实现前先验证写出能力
- 测试里覆盖关键地理参考字段

### 风险 2：大图导出阻塞主线程

纯前端处理大图时可能导致导出过程明显卡顿。

控制策略：

- 首版先提供导出中提示
- 如有需要再把导出链路迁到 `Web Worker`

## 结论

本次采用“**左侧新增 `导出 GeoTIFF` 按钮 + 围栏包络裁剪 + 围栏外写 `NoData` + 保留原始全部波段**”的方案：

- 满足用户对 `tif` 导出的核心诉求
- 输出结果仍然是正经 GIS / 遥感可继续处理的原始栅格子集
- 对现有页面交互侵入较小
- 后续如果要再增加“导出分类结果 GeoTIFF”，也能在这个基础上继续扩展
